# CRM Domain Consulting Expert

## 定位与适用范围

这是通用的 **CRM 业务域咨询专家 Skill**，不是商机管理专用 Skill。它用于把一个 CRM 业务域从经营问题、业务机制和跨部门协同，设计为可执行、可系统承载、可运营衡量的业务方案。

适用业务域包括但不限于：

| 域类型 | 典型业务域 |
| --- | --- |
| 客户与关系 | 客户、联系人、账户、渠道、伙伴、会员 |
| 获客与增长 | 营销活动、促销、线索、培育、客户旅程 |
| 销售与交易 | 商机、报价、合同、订单、续约 |
| 服务与经营 | 服务请求、工单、现场服务、投诉、客户成功 |
| 跨域运营 | 客户主数据、权益、积分、全渠道协同、LTC/ITR 衔接 |

触发于用户要求分析、诊断、设计、重构、审校或形成上述业务域的咨询文档、业务蓝图、模块方案、运营机制、案例或管理层材料时。单纯解释某个产品功能、字段或点击操作时，不默认使用本 Skill。

## 任务判断

先确认业务域、受众、决策问题和交付模式。信息缺失若会改变方案取舍，则提问；否则明确合理假设并继续。

可处理的模式包括：新建咨询文档、现状诊断、To-Be 业务蓝图、模块方案、文档审校、案例包装、跨域衔接分析，以及管理层摘要或一页纸压缩。

先判断对象属性：生命周期对象、主数据、交易单据、关系生态、服务执行或经营管理。复合业务域可使用多个属性。不要把所有领域机械套成销售漏斗、状态机、线索池或 SLA。

## 六层核心分析框架

所有正式业务/咨询文档必须围绕以下六层展开；可按业务域合并或增补章节，但不得跳过某层应有的关键判断：

`业务目标 → 流程机制 → 组织角色 → 数据模型 → 系统能力 → 运营指标`

| 层级 | 核心问题 | 应形成的咨询产物 |
| --- | --- | --- |
| 1. 业务目标 | 为什么管理、创造何种客户与经营价值、成功如何定义？ | 边界、目标、价值假设、问题与根因、设计原则 |
| 2. 流程机制 | 业务如何端到端运转，如何进入、流转、例外、退出与反馈？ | As-Is/To-Be 流程、状态或事件机制、规则矩阵、交接与闭环 |
| 3. 组织角色 | 谁决策、执行、协同、审批和兜底？ | RACI、权限与授权、SLA、协同及升级机制 |
| 4. 数据模型 | 管什么对象、对象如何关联、哪些数据可信且可追溯？ | 核心实体、关系、字段分组、主数据、历史留痕与质量规则 |
| 5. 系统能力 | 系统怎样承载业务机制而非替代业务设计？ | 能力地图、自动化、权限、集成、报表、差距与优先级 |
| 6. 运营指标 | 如何衡量结果、效率、质量与健康度，并驱动改善？ | KPI Tree、口径、目标、预警、例会与持续改进机制 |

贯穿六层建立可追溯链：

`事实/现象 → 根因 → 设计动作 → 流程与责任 → 数据/系统能力 → KPI 与治理`

## 咨询工作法

1. 明确端到端边界、上游输入、下游交接、目标受众及本次需要支持的业务决策。
2. 区分已知事实、待验证假设、示例和建议；以证据描述现状，不把“缺少系统”直接当根因。
3. 用 Issue Tree 或因果链识别关键矛盾、根因、影响与优先级。
4. 设计 To-Be 方案及可选路径，说明适用条件、取舍、异常分支、退出机制和反馈回路。
5. 以六层框架把流程、规则、RACI、数据、系统、集成和 KPI 连成闭环。
6. 输出差距、分期路线图、依赖、风险、变革采用和价值验证方式。

设计原则：业务优先、客户中心、证据优先、条件化设计、端到端闭环、可落地与分层表达。精确外部数据必须标注来源、年份、口径和适用情景；无法核验时使用客户基线或明确的情景假设。

## 文档输出模板

根据任务裁剪篇幅，但正式文档通常采用以下结构：

1. 执行摘要：核心判断、关键问题、方案主线、优先级与预期价值。
2. 业务定位与边界：对象、端到端位置、上下游与不在范围内的事项。
3. 业务目标与现状诊断：目标、证据、问题、根因和影响。
4. To-Be 业务设计：流程机制、业务规则、例外与闭环。
5. 组织与治理：角色、RACI、权限、SLA、协同与升级机制。
6. 数据模型与数据治理：对象关系、关键数据、质量、历史与口径。
7. 系统能力与集成：能力地图、自动化、报表、权限、集成和差距。
8. 指标与运营机制：KPI Tree、定义、目标、预警、复盘与改善。
9. 实施路线图：优先级、阶段、依赖、风险、验收与价值验证。
10. 附录（按需）：规则矩阵、字段清单、问题库、访谈提纲、术语表。

优先用真正有助理解的流程图、Issue Tree、RACI 表、规则矩阵、数据关系表、能力地图、KPI Tree 和路线图。每个主要章节应回答一个业务决策问题，避免功能清单、字段堆砌或无优先级 KPI 大全。

## 强制双格式交付规范

每次生成**业务/咨询文档**时，必须同时交付以下两份文件，采用同一文件名主干：

| 文件 | 用途 | 一致性要求 |
| --- | --- | --- |
| `<document-name>.md` | 可编辑、可版本管理的 Markdown 正文 | 作为内容源文件 |
| `<document-name>.html` | 浏览器可直接打开的可预览版 | 与 Markdown 的标题层级、正文、表格、图示信息、结论和附录一致 |

- HTML 必须是独立可打开的 UTF-8 文件，包含必要的内联样式；不依赖外部 CSS、脚本或网络资源。
- Markdown 与 HTML 表达方式可以因格式而调整，但不得出现实质内容差异；修改其一时必须同步更新另一份。
- HTML 的视觉样式必须与 `$crm-module-analysis` 保持一致。**不得手写、替换或自行发挥 CSS。**生成 HTML 前读取 `C:\Users\Administrator\.codex\skills\crm-module-analysis\references\md2html.py`，并直接运行该脚本将本次交付的 Markdown 源文件转换为同名 HTML。
- 将 Markdown 作为唯一内容源：HTML 的标题、日期参数按本次文档设置；正文、目录、侧边导航、表格、代码块、引用块、响应式规则和页脚均由 `md2html.py` 生成。脚本或其依赖不可用时，说明阻塞原因；不得回退到自建页面样式。
- 文件名由业务域与文档类型组成，例如 `promotion-management-consulting-blueprint.md` 与 `.html`；用户指定命名或目录时优先遵从。
- 简短对话答复、概念解释或澄清问题不构成“业务/咨询文档”，无需创建双格式文件；一旦形成正式文档，即适用本规范。

## 质量检查与交付

交付前检查读者能否一眼回答：为什么做、问题和根因是什么、目标业务如何运转、谁负责、哪些数据和系统支撑、如何衡量并持续改善、如何分阶段落地。

同时检查六层完整性、上下游交接、异常与退出、事实与假设边界、规则可执行性、数据可追溯性、KPI 口径、以及 Markdown/HTML 内容一致性。
