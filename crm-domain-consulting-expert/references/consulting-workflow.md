# CRM 咨询工作流

用于新建咨询文档、现状诊断和业务蓝图。按任务裁剪，不把流程机械扩成大而全手册。

## 1. 咨询主链路

```text
业务目标与决策问题
        ↓
范围、对象与利益相关方
        ↓
As-Is 事实与证据
        ↓
问题树与根因
        ↓
设计原则与方案取舍
        ↓
To-Be 业务运行机制
        ↓
组织 / 规则 / 数据 / 系统 / 指标
        ↓
治理、反馈、采用与路线图
        ↓
价值验证与持续改进
```

系统是业务机制的承载者，不应在目标、问题和根因尚未明确时先列功能。

## 2. 定位与范围

先确认文档要支持什么决策，而不只是确认模块名称。

至少识别：

- 业务域在端到端流程中的位置、上游、下游和交接对象；
- 服务的客户类型、产品、区域、渠道和业务模式；
- 核心业务对象及其关系；
- 业务负责人、使用角色、协同部门和决策者；
- 本次范围内与范围外内容；
- 需要解决的管理决策，如增长、预测、效率、合规、体验或成本。

可用四问快速建立骨架：

1. 为什么企业需要这个业务域？
2. 它创造什么客户价值与经营价值？
3. 它应该如何运转和管控？
4. 用什么结果与指标判断有效？

## 3. 业务目标与成功标准

把抽象目标转成可观察的管理结果。

| 抽象诉求 | 应追问的管理结果 |
|---|---|
| 提升销售效率 | 减少哪些等待、重复或低价值动作？ |
| 提升预测准确性 | 哪类预测、什么周期、由谁使用？ |
| 提升客户体验 | 客户旅程中的哪个结果需要改善？ |
| 建立统一客户视图 | 哪些决策因数据割裂而失败？ |
| 加强过程管理 | 哪些阶段、责任或证据当前不可见？ |

成功标准应尽量包含基线、目标方向、使用者和管理动作。没有可靠基线时，不编造目标数字，先提出数据校准方法。

## 4. As-Is 现状与证据

从七个维度描述现状：

| 维度 | 关注内容 |
|---|---|
| 业务结果 | 当前结果、基线、波动和管理影响 |
| 流程 | 真实路径、等待、返工、异常和线下动作 |
| 组织 | 角色、责任、协作冲突、授权和升级 |
| 规则 | 定义、准入退出、审批、分配、例外和时限 |
| 数据 | 对象、口径、重复、历史、审计、权限和质量 |
| 系统 | 系统边界、手工台账、集成、自动化和体验 |
| 运营指标 | 看板、复盘节奏、责任人和纠偏动作 |

将内容标记为：已确认事实、用户判断、待验证假设、外部参考。访谈表述不能自动升级为企业事实。

## 5. 问题与根因分析

不要将“缺少 CRM 功能”“没有流程”直接作为根因。使用 Issue Tree 检查：

```text
业务结果不理想
├─ 战略与目标：目标或客户策略不清
├─ 流程：路径、交接、异常或闭环缺失
├─ 组织：责任、能力、授权或资源不匹配
├─ 规则：定义、标准、审批、分配或激励不合理
├─ 数据：对象、口径、质量、历史或权限有问题
├─ 系统：能力、集成、自动化或易用性不足
├─ 运营：执行、培训、复盘和改进机制不足
└─ 指标：测量错误、归因错误或没有驱动行动
```

一条完整问题链应包含：

`现象 → 业务影响 → 证据 → 直接原因 → 深层原因 → 需要支持的决策`

## 6. 设计原则与方案取舍

To-Be 前先提出少量设计原则，例如：客户中心、单一口径、端到端负责、例外可控、数据留痕、分层治理、优先标准化。

对存在多种合理做法的设计，用选项表表达：

| 选项 | 适用条件 | 优点 | 风险/代价 | 推荐判断 |
|---|---|---|---|---|

避免把线索池、BANT、固定 SLA、审批流或某个阶段模型写成所有企业的必选方案。

## 7. To-Be 业务运行机制

流程设计不只是先后顺序。至少定义五部分：

`业务路径 + 组织责任 + 输入输出 + 执行规则 + 管控机制`

### 7.1 业务路径

- 明确触发、主要节点、决策点、交接、异常、退出和完成结果；
- 生命周期对象可使用状态机，但主数据和交易单据还需分别考虑治理、版本和审批；
- 关键阶段应对应业务事实或客户里程碑，而不是只有内部动作名称；
- 关闭、退回、重开、变更和撤销要有原因、责任和历史。

### 7.2 节点设计

对关键节点定义：

| 要素 | 需要回答的问题 |
|---|---|
| 目的 | 为什么存在这个节点？ |
| 输入 | 进入前必须具备什么？ |
| 活动 | 哪些角色完成什么动作？ |
| 规则 | 进入、退出、审批、时限和例外是什么？ |
| 输出 | 形成什么业务结果和数据证据？ |
| 系统承载 | 校验、工作流、审批、提醒、权限如何支持？ |
| 衡量 | 用什么指标判断有效？ |

规则尽量写成：`触发条件 → 执行动作 → 责任角色/系统 → 结果 → 例外与升级`。

### 7.3 组织与责任

- RACI 的行优先对应真实业务活动或关键决策；
- 区分业务所有者、流程所有者、数据所有者和系统所有者；
- 跨部门交接应定义双向责任与反馈，而不是单向“甩单”；
- 对重大定义、阈值和例外设置治理责任与复盘节奏。

### 7.4 数据与历史

- 识别核心对象、关系、主数据、交易数据、事件和历史记录；
- 区分当前状态与历史事件，避免用一个字段同时承担事实、阶段和履历；
- 关键决策应保留来源、时间、责任人、变更原因和审计记录；
- 同意、评分、分配、阶段、状态、审批和归属通常需要历史留痕；
- 数据字段必须服务流程、规则、分析或合规，不因“可能有用”无限增加。

### 7.5 系统与集成

按业务能力而不是产品菜单描述系统：记录、校验、路由、协同、审批、提醒、分析、权限和审计。

每个集成明确：源系统、目标系统、业务对象、触发时点、主责系统、失败处理和对账机制。

### 7.6 KPI Tree 与治理

```text
业务结果指标
├─ 漏斗/过程结果指标
├─ 效率与时效指标
└─ 诊断与健康指标
```

每项核心 KPI 说明定义、公式、口径、维度、频率、责任人、管理动作和防刷风险。指标必须对应决策，不能只做报表。

治理至少包括：定义维护、数据质量、流程例外、指标复盘、方案优化和变更批准。加入反馈回路，使前端获客、销售、履约、服务和产品改进能够闭环。

## 8. 差距、路线图与价值

用差距矩阵连接现状与目标：

| 目标能力 | 当前差距 | 业务影响 | 建设动作 | 优先级 | 依赖 | 责任方 |
|---|---|---|---|---|---|---|

路线图可分为：

1. **基础统一**：定义、对象、流程责任和数据口径；
2. **闭环落地**：核心流程、规则、系统和集成；
3. **运营提升**：指标、预测、自动化和治理；
4. **持续优化**：模型校准、体验提升和跨域协同。

价值表达同时包含客户价值、经营价值、管理能力和风险控制。ROI 使用情景区间和敏感性分析，不使用“无法反驳”等过度承诺。

## 9. 复杂方案与案例表达

复杂方案案例使用六段结构：

1. 背景与业务目标；
2. 业务问题和影响；
3. 根因与约束；
4. 方案设计及关键取舍；
5. 实施难点、协同和落地机制；
6. 结果、价值和复盘。

把实施经历从“配置了哪些功能”升级为“如何解决业务管理问题”，但不得虚构职责、难点或项目效果。

## 10. 追溯矩阵

重要方案使用以下矩阵自检：

| 业务问题/根因 | 设计动作 | 流程/组织变化 | 数据与系统能力 | KPI | 路线阶段 |
|---|---|---|---|---|---|

无法建立追溯关系的功能、字段和指标，应重新判断是否必要。
